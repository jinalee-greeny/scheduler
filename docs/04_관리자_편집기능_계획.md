# 프로젝트 관리자(PM) 수정·생성·설정 기능 계획

> 프로젝트: 02. 일정관리자 · pxd
> 작성 기준일: 2026-07-15
> 목적: 지금은 Claude가 데이터를 고쳐 재생성해야만 반영되는 구조를, **PM이 직접 수정·생성·설정**할 수 있는 구조로 어떻게 발전시킬지 정리

---

## 1. 지금 구조와 한계

현재 대시보드(`일정관리_시스템.html`)는 데이터(WBS·공수·일정)가 파일 안 JSON에 **읽기 전용**으로 박혀 있고, 역산 스케줄·M/M 계산은 파이썬(`wbs_calc.py`)이 미리 돌려 두 시나리오(주말 on/off)를 넣어 둡니다. 화면은 그 결과를 보여줄 뿐입니다.

그래서 지금은 태스크 하나를 바꾸려 해도 (1) 파이썬 데이터 수정 → (2) 재계산 → (3) 재생성의 과정을 Claude가 대신해야 합니다. **PM이 브라우저에서 직접 바꾸는 것은 불가능**합니다. 이 문서는 그 통제권을 PM에게 넘기는 계획입니다.

---

## 2. PM이 직접 하게 만들 3가지

요청하신 "수정·생성·설정"을 구체 범위로 나누면 이렇습니다.

**수정(Edit)** — 기존 태스크의 이름·담당·공수(MD)·기간·선행관계·상태·진행률 변경, 일정 조정, 완료 처리. 변경하면 역산 일정·크리티컬 패스·M/M이 **자동 재계산**되어야 함.

**생성(Create)** — 새 태스크·새 단계(Phase) 추가, 새 프로젝트(다른 프로젝트도 같은 틀로) 생성, 태스크 복제.

**설정(Configure)** — 프로젝트 기본값과 규칙을 바꾸는 것. 목표 오픈일·버퍼, 근무 캘린더(주말 on/off·공휴일), 분류값과 색상(단계·상태·우선순위·유형), 역할과 M/M 기준(1 M/M=며칠, 가동률), 그리고 **누가 무엇을 할 수 있는지(권한)**.

---

## 3. 핵심 설계 결정 — 계산 엔진을 옮긴다

가장 중요한 결정입니다. 지금은 계산이 파이썬(빌드 타임)에 있어 편집과 분리돼 있습니다. PM이 편집하는 순간 결과가 바뀌려면, **역산 스케줄링·slack·크리티컬 패스·M/M 계산 로직을 편집이 일어나는 곳(브라우저 또는 서버)으로 이동**해야 합니다.

계산 규칙 자체(근무일 계산, ALAP 역산, 버퍼, 공휴일 제외)는 이미 `wbs_calc.py`에 정의돼 있으므로, 이를 JavaScript(1단계) 또는 서버 API(3단계)로 1:1 이식하면 됩니다. 즉 **로직은 이미 검증됨 — 옮기기만 하면 됩니다.**

---

## 4. 권한 모델

관리 기능은 권한과 세트입니다. 최소 3단계를 권장합니다.

| 역할 | 수정 | 생성 | 설정 | 조회 |
|---|---|---|---|---|
| 관리자(PM·Admin) | ● 전체 | ● 전체 | ● 전체(권한·분류·캘린더 포함) | ● |
| 편집자(Editor·팀원) | ● 담당 태스크 | ● 태스크 추가 | △ 개인 뷰 설정만 | ● |
| 뷰어(Viewer) | ✕ | ✕ | ✕ | ● |

설정(프로젝트 규칙·권한·분류 관리)은 **관리자 전용**으로 두는 것이 핵심입니다. 편집자는 자기 일 위주로, 뷰어는 보기만.

---

## 5. 단계별 로드맵

인프라 부담과 필요 시점을 고려해 3단계로 나눕니다. 1단계만으로도 "PM이 직접 편집"은 달성됩니다.

### 1단계 — 단일 HTML "편집 모드" (백엔드 없음, 즉시 가능)

지금 파일에 편집 UI를 붙입니다.

- **편집 모드 토글**: 평소엔 보기 전용, 관리자가 "편집 모드"를 켜면 태스크 등록·수정·삭제 폼과 설정 패널이 열림.
- **태스크 CRUD 폼**: 이름·담당·MD·소요일·선행·상태·진행률 입력. 저장 시 브라우저에서 즉시 재계산(3장 JS 엔진).
- **설정 패널**: 목표 오픈일/버퍼, 주말 on/off, 공휴일 목록 편집, 분류값·색상, 역할·M/M 기준 편집.
- **저장/불러오기**: 데이터를 **JSON 파일로 내보내기/가져오기**. (단일 HTML은 서버가 없으므로 파일이 저장 매체 — 이 JSON을 프로젝트에 올려두면 다음에 이어서 편집)
- 대상: PM 1인이 직접 운영하는 시나리오. 인프라 0, 가장 빠름.
- 한계: 실시간 다중 사용자 동시 편집·자동 서버 저장·로그인은 없음(파일 기반).

### 2단계 — 경량 저장·이력

1단계 위에 "잃어버리지 않게" 얹습니다.

- 자동 저장(브라우저 저장소 또는 간단한 파일 동기화), 변경 이력(누가 언제 무엇을), 되돌리기(undo).
- 여전히 단일 사용자~소규모. 로그인은 선택.

### 3단계 — 정식 웹앱 (팀 운영·다중 사용자)

여러 명이 동시에 쓰고, 권한·저장·알림이 필요할 때.

- **백엔드 + DB**: 태스크·설정·사용자 저장. 편집 시 서버가 재계산.
- **로그인·권한**: 4장 역할 모델 적용(관리자/편집자/뷰어).
- **동시 편집·감사 로그·알림**: 변경 알림, 마감 리마인더, 활동 기록.
- 앞서 만든 화면기획서·기획서의 "설정 화면·권한" 항목이 여기서 실제 구현됩니다.

---

## 6. 설정 화면 상세 (관리자 전용)

3장 "설정"에서 관리자가 바꾸는 항목을 화면 기준으로 정리하면:

| 설정 그룹 | 항목 | 바뀌면 영향 |
|---|---|---|
| 프로젝트 | 프로젝트명, 목표 오픈일, 버퍼(근무일) | 역산 일정·D-day 전체 재계산 |
| 근무 캘린더 | 주말 근무 on/off, 공휴일 추가·삭제 | 근무일 산정·일정 이동 |
| 공수 기준 | 1 M/M = N인일, 역할별 가동률 | M/M 집계·기간 |
| 분류·색상 | 단계, 상태, 우선순위, 유형, 색상 매핑 | 뱃지·간트·필터 |
| 조직·권한 | 역할, 담당자, 접근 권한 | 편집 가능 범위 |

이 값들을 코드에 하드코딩하지 않고 **설정 데이터로 분리**해 두면, 화면 여러 곳(간트·목록·M/M)이 같은 설정을 참조하게 되어 일관성이 유지됩니다(이미 데이터-분리 구조로 전환해 둠).

---

## 7. 데이터 안전장치 (편집 허용 시 필수)

PM이 자유롭게 고칠 수 있게 되면, 잘못된 입력을 막는 규칙이 함께 필요합니다.

핵심 검증으로 태스크명 공백 금지, MD·소요일은 양수, 종료일 ≥ 시작일, 상태·유형은 정해진 값만 허용을 두고, 선행관계는 **순환 의존성(A→B→A) 자동 차단**과 존재하는 태스크 ID만 참조하도록 검사합니다. 여기에 되돌리기(undo)와 저장 전 백업(직전 JSON 보관)을 더하면 실수로 인한 손실을 막을 수 있습니다.

---

## 8. 추천 진행안

바로 실효를 보려면 **1단계(단일 HTML 편집 모드)**부터 만드는 것을 추천합니다. 지금 구조가 이미 데이터-분리형이라 계산 로직을 JS로 이식하고 편집 폼·설정 패널만 얹으면 되며, 인프라 없이 PM이 직접 수정·생성·설정을 할 수 있습니다. 팀 여러 명이 동시에 쓰고 로그인·권한·서버 저장이 필요해지는 시점에 3단계 웹앱으로 확장하면 됩니다.

**다음 스텝(결정해 주시면 진행):**
1. 1단계 "편집 모드"를 지금 대시보드에 바로 붙일까요? (태스크 CRUD + 설정 패널 + 클라이언트 재계산 + JSON 내보내기)
2. 권한은 3단계(관리자/편집자/뷰어)로 갈까요, 우선 관리자 단독으로 단순화할까요?
3. 최종 목표가 **팀 다중 사용자 웹앱**이라면, 3단계 기준의 기술 아키텍처(백엔드·DB·인증) 설계도 별도로 그려 드리겠습니다.
