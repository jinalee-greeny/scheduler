# 일정관리 시스템 — 정식 스택 마이그레이션 설계서

> 프로젝트: 02. 일정관리자 · pxd
> 작성 기준일: 2026-07-15
> 목적: 현재 "단일 HTML 프로토타입"을 **React + 백엔드(API·DB·인증)** 기반 프로덕션 웹앱으로 이관하기 위한 아키텍처 설계. 이미 검증된 계산 엔진과 데이터 모델을 재사용하는 것이 핵심.

---

## 1. 전제 — 무엇을 가져가고 무엇을 바꾸는가

현재 산출물에는 **버릴 것이 거의 없습니다.** 지금 단일 HTML 안에는 (1) 역산 스케줄링·M/M 계산 엔진(JS), (2) 데이터 모델(`wbs_model.json`), (3) 화면 로직이 이미 검증된 상태로 들어 있습니다. 마이그레이션의 본질은 새로 만드는 것이 아니라, 이 세 가지를 **각자 제자리(공유 패키지 / DB / React 컴포넌트)로 옮기고, 다중 사용자·저장·권한을 얹는 것**입니다.

바뀌는 건 "어디서 계산하고 어디에 저장하느냐"입니다. 지금은 브라우저 메모리에서 계산하고 파일(JSON)로 저장하지만, 프로덕션에서는 **엔진을 클라이언트·서버가 공유**하고 **DB에 저장**하며 **로그인·권한**으로 접근을 통제합니다.

## 2. 목표 아키텍처 (3-tier)

```
┌────────────────────────────────────────────────────────────┐
│  Frontend (React + TS)                                      │
│   - 간트/WBS/M/M 뷰, 편집 폼, 설정                          │
│   - 편집 시 @scheduler로 즉시 미리보기(낙관적 재계산)       │
└───────────────▲──────────────────────────┬─────────────────┘
                │  REST/tRPC (JSON)         │
                │                           ▼
┌───────────────┴────────────────────────────────────────────┐
│  Backend API (Node + TS)                                    │
│   - 인증/권한(RBAC), 검증, 저장, 감사로그                   │
│   - 저장 시 @scheduler로 '정본' 재계산 후 응답             │
└───────────────▲──────────────────────────┬─────────────────┘
                │  SQL (Prisma)             │
                ▼                           ▼
┌────────────────────────────────────────────────────────────┐
│  PostgreSQL  — projects, tasks, deps, phases, holidays,     │
│               users, memberships(role), audit_log           │
└────────────────────────────────────────────────────────────┘
                ▲
                │  import (동일 코드)
        ┌───────┴────────┐
        │  @scheduler    │  ← 프론트·백엔드가 공유하는 순수 계산 패키지
        │  (현재 JS엔진) │
        └────────────────┘
```

**핵심 원칙:** 계산 엔진 `@scheduler`를 프론트와 백엔드가 **동일 코드로 공유**합니다. 프론트는 편집 중 즉각 미리보기를 위해, 백엔드는 저장 시 "정본(authoritative)" 값을 확정하기 위해 같은 함수를 호출합니다. 계산 규칙이 두 곳에서 어긋날 일이 없습니다.

## 3. 기술 스택 추천

| 계층 | 추천 | 이유 / 대안 |
|---|---|---|
| 공유 엔진 | **TypeScript 패키지 `@scheduler`** | 현재 JS 엔진을 TS로 이식. 프론트·백엔드 공유의 전제. |
| 프론트엔드 | **React + TypeScript + Vite** | 컴포넌트화·타입 안전. 대안: Next.js(SSR 필요 시). |
| 상태/데이터 | **TanStack Query**(서버상태) + **Zustand**(로컬 편집상태) | 서버 동기화와 낙관적 업데이트에 최적. |
| 스타일 | **Tailwind CSS** | 현재 스타일 톤 이식 용이. |
| 간트 | **커스텀 컴포넌트**(현 로직 재사용) 또는 경량 라이브러리 | 지금 간트 렌더 로직을 React로 포팅 권장. |
| 백엔드 | **Node.js + NestJS(TS)** | 엔진 코드 공유가 가능(동일 언어). 대안: Express(경량), 또는 **FastAPI(Python)** — 그 경우 `wbs_calc.py`를 정본으로. |
| DB | **PostgreSQL** | 관계형·트랜잭션·감사에 적합. |
| ORM | **Prisma** | 스키마·마이그레이션·타입 자동생성. |
| 인증 | **세션 or JWT + RBAC** | 소규모는 세션(쿠키)이 단순. SSO 필요 시 OIDC. |
| 배포 | **Vercel(프론트) + 관리형 Postgres(Neon/Supabase/RDS)** 또는 컨테이너(Docker) | 팀 규모·보안 요건에 따라. |

> 언어 선택 팁: **엔진 공유 이점을 살리려면 백엔드도 TS(Node)** 가 유리합니다. 사내 표준이 Python이면 FastAPI + `wbs_calc.py`를 정본 엔진으로 삼고, 프론트는 미리보기용으로 TS 포팅본을 두되 **골든 테스트로 두 엔진의 동치를 보장**하세요.

## 5. 계산 엔진 이관 (가장 중요)

현재 HTML 안 `compute(mode)` / `rollup()` 로직을 그대로 **순수 함수 패키지**로 승격합니다. 전역 `MODEL`을 인자로 받도록만 바꾸면 됩니다(이미 그 형태에 가깝습니다).

```ts
// packages/scheduler/src/index.ts
export type Mode = 'off' | 'on';
export type Status = '예정'|'진행중'|'완료'|'보류'|'취소';

export interface Task { id:string; name:string; phase:string; role:string;
  md:number; dur:number; deps:string[]; status:Status; }
export interface Settings { today:string; bufferWd:number; mdPerMm:number; }
export interface Model { settings:Settings; holidays:{date:string;name:string}[];
  phases:{id:string;name:string;color:string}[]; tasks:Task[]; }

export interface TaskState { es:string|null; ef:string; ls:string; lf:string;
  slack:number|null; critical:boolean; }
export interface ScheduleResult { target:string; asap:string; dday:number;
  minSlack:number; critical:string[]; task:Record<string,TaskState>; }

export function computeSchedule(model:Model, mode:Mode): ScheduleResult;  // 역산 ASAP/ALAP/slack/CP
export function rollupMM(model:Model): { total:number; done:number; remain:number;
  progress:number; byPhase:Record<string,number>; byRole:Record<string,number>; };
```

이렇게 분리하면 프론트(미리보기)·백엔드(정본)·테스트가 **같은 함수**를 씁니다. 순환 의존성 검사(`hasCycle`)와 검증 규칙도 이 패키지에 함께 둡니다.

## 6. 데이터 모델 → DB 스키마

현재 `wbs_model.json`(단일 프로젝트)을 **다중 프로젝트·다중 사용자** 관계형으로 확장합니다.

| 테이블 | 주요 컬럼 | 비고 |
|---|---|---|
| `project` | id, name, anchor_date(오늘 기준), buffer_wd, md_per_mm, weekend_default | 프로젝트별 설정 |
| `phase` | id, project_id, wbs_no, name, color, order | 단계 |
| `task` | id, project_id, wbs_id, name, phase_id, role, md, dur, status | 태스크 |
| `task_dependency` | task_id, depends_on_task_id | 선행관계(N:N) |
| `holiday` | id, project_id(nullable=공용), date, name | 공휴일 |
| `user` | id, email, name | 사용자 |
| `membership` | user_id, project_id, role(admin/editor/viewer) | 프로젝트별 권한 |
| `audit_log` | id, project_id, user_id, action, entity, before(jsonb), after(jsonb), at | 변경 이력 |

```prisma
model Task {
  id       String  @id @default(cuid())
  project  Project @relation(fields:[projectId], references:[id])
  projectId String
  wbsId    String            // "3.3"
  name     String
  phaseId  String
  role     String
  md       Int
  dur      Int
  status   String
  deps     TaskDependency[] @relation("from")
  @@unique([projectId, wbsId])
}
model TaskDependency {
  fromId String; toId String
  from   Task @relation("from", fields:[fromId], references:[id])
  @@id([fromId, toId])
}
```

> 계산 결과(ES/EF/LS/LF·CP·M/M)는 **저장하지 않고 요청 시 엔진으로 계산**하는 것을 기본으로 합니다(항상 최신·정합). 대형 프로젝트에서 성능이 문제되면 저장(캐시) + 무효화 전략을 도입합니다.

## 7. API 설계 (REST 예시)

| 메서드 · 경로 | 설명 | 권한 |
|---|---|---|
| `GET /projects/:id` | 프로젝트+태스크+설정 조회 (+계산결과 포함) | viewer↑ |
| `POST /projects/:id/tasks` | 태스크 생성 | editor↑ |
| `PATCH /tasks/:id` | 태스크 수정 | editor↑(담당) |
| `DELETE /tasks/:id` | 태스크 삭제(+deps 정리) | editor↑ |
| `PATCH /projects/:id/settings` | 설정(버퍼·M/M기준·기준일) 변경 | admin |
| `POST /projects/:id/holidays` `DELETE …` | 공휴일 추가·삭제 | admin |
| `POST /projects/:id/recompute` | 정본 재계산 결과 조회(읽기전용) | viewer↑ |
| `GET /projects/:id/export` · `POST …/import` | JSON 내보내기·가져오기 | admin |
| `GET /projects/:id/audit` | 변경 이력 | admin |

저장 계열 요청은 서버에서 **검증(필수값·순환의존성) → 트랜잭션 저장 → `@scheduler` 재계산 → 결과 반환 → 감사로그 기록** 순으로 처리합니다. tRPC를 쓰면 프론트-백엔드 타입을 자동 공유할 수 있습니다.

## 8. 회귀 테스트 (엔진 정합성 보증)

이관 시 반드시 지켜야 할 "골든 값"입니다. 현재 데이터 기준으로 테스트를 고정해, 리팩터링/포팅 후에도 계산이 동일함을 보장합니다.

| 시나리오 | 기대값 |
|---|---|
| 총 공수 | 124 MD = 6.2 M/M |
| 완료 | 28 MD (23%) |
| 주말 제외(off) 목표 오픈 | 2026-09-23 (ASAP 09-16 + 버퍼 5) |
| 주말 포함(on) 목표 오픈 | 2026-09-04 (ASAP 08-30) |
| 크리티컬 패스 | 12개 태스크 (3.1→…→7.2) |
| 3.3 공수 10→20 변경 시 목표(off) | 2026-10-06 |

```ts
test('golden: off 목표=2026-09-23, CP=12', () => {
  const r = computeSchedule(model, 'off');
  expect(r.target).toBe('2026-09-23');
  expect(r.critical.length).toBe(12);
});
```

## 9. 인증·권한(RBAC)

3장의 역할을 서버에서 강제합니다.

| 역할 | 조회 | 태스크 수정·생성 | 설정·권한·공휴일 |
|---|---|---|---|
| admin(PM) | ● | ● 전체 | ● |
| editor(팀원) | ● | ● (담당/허용 범위) | ✕ |
| viewer | ● | ✕ | ✕ |

권한 검사는 **프론트 숨김 + 백엔드 강제**를 이중으로 둡니다(프론트만 막으면 우회 가능). 미들웨어에서 `membership.role`로 엔드포인트를 게이트합니다.

## 10. 마이그레이션 단계 (현재 → 프로덕션)

앞서 정리한 1·2·3단계와 이어집니다. 각 단계가 **독립적으로 배포 가능한 산출물**을 냅니다.

| 단계 | 내용 | 산출 |
|---|---|---|
| P0. 엔진 추출 | 현재 JS 엔진 → `@scheduler`(TS) + 골든 테스트 | 공유 패키지 |
| P1. 앱 골격 | React 앱이 `@scheduler`로 현 대시보드 재현(로컬 상태) | 컴포넌트화된 프론트 |
| P2. API+DB | NestJS+Postgres, 단일 프로젝트 CRUD·저장 | 서버 저장 |
| P3. 인증·권한 | 로그인 + RBAC + 감사로그 | 다중 사용자 |
| P4. 협업·알림(옵션) | WebSocket 동시 편집, 마감 알림 | 팀 운영 |

현재 자산이 그대로 각 단계의 출발점이 됩니다: **엔진→P0, 모델→P2 스키마, 화면 로직→P1 컴포넌트.**

## 12. 결정이 필요한 사항

진행 전 정해두면 좋은 선택지입니다.

첫째, **백엔드 언어** — 엔진 공유 이점을 위해 Node(TS)로 갈지, 사내 표준이면 Python(FastAPI)+`wbs_calc.py`로 갈지. 둘째, **배포 환경** — 관리형(Vercel+Neon 등) 대 사내 인프라(보안·망분리 요건). 셋째, **인증 방식** — 자체 계정 대 사내 SSO(OIDC/SAML). 넷째, **협업 실시간 편집** 필요 여부(있으면 P4에서 WebSocket).

원하시면 이 설계 기준으로 **P0(엔진 패키지 + 골든 테스트) 스타터 코드**를 실제로 만들어 드리거나, 선택하신 스택에 맞춘 세부 스키마·API 명세로 더 내려가겠습니다.
